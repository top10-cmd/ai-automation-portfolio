# Интеграции и границы MVP

## OpenAI Responses

Сервер вызывает фиксированный endpoint `https://api.openai.com/v1/responses` с `store:false`, `text.format` / JSON Schema / `strict:true`. Ключ и выбранная модель берутся только из переменных окружения. Ошибка, отказ модели, незавершённый ответ и некорректные поля завершаются ошибкой; скрытой подмены на mock нет. Модель не получает инструменты отправки и не может менять статусы.

Контракт адаптера проверен с подставными ответами. Настоящий API не вызывался: для этого нужен ключ и доступная модель с поддержкой Structured Outputs. Семантическая точность языка/резюме требует проверки на реальном провайдере; схема контролирует структуру, а не истинность.

Основа реализации: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

## CRM

Указать HTTPS-адрес `CRM_WEBHOOK_URL` и при необходимости `CRM_WEBHOOK_TOKEN`. После подтверждения передаётся только утверждённый ответ и классификация, без исходного обращения:

```json
{
  "event": "support.approved",
  "eventId": "ticket-uuid",
  "synthetic": true,
  "ticket": { "id": "ticket-uuid", "languageCode": "en", "category": "delivery", "urgency": "high", "reply": "Approved reply" }
}
```

Заголовок `Idempotency-Key` равен `eventId`. Получатель должен сохранять этот ключ и игнорировать повторы. Сервер блокирует параллельную повторную отправку, но не обещает exactly-once доставку через сеть. При таймауте результат неизвестен: оператор проверяет CRM и при необходимости повторяет тот же payload с тем же ключом. После первой попытки текст заморожен. HTTP 2xx означает приём события CRM, а не доставку сообщения клиенту.

После перезапуска тексты не восстанавливаются: сохранённый статус `delivering` требует ручной сверки с CRM. Автоматической повторной отправки при запуске нет.

## n8n

`n8n-workflow.json` — подготовленный шаблон **приёма** обращения. JSON и структура соединений проверены, импорт и выполнение внутри n8n в этой среде не проверялись. `automation-flow.json` описывает полный эквивалент процесса, реализованный локальным сервером и интерфейсом.

Поток n8n: Webhook → проверка synthetic → HTTP `/api/analyze` → Respond to Webhook. Он возвращает обращение со статусом `review`. Оператор открывает журнал в LinguaDesk и подтверждает ответ вручную. Узел Webhook не используется как промежуточное ожидание, автоматической стрелки к отправке нет.

Для локального подключения:

1. Запустить n8n нативно на том же компьютере, где работает LinguaDesk. Этот MVP слушает только `127.0.0.1`: n8n Cloud и контейнер на другом сетевом интерфейсе не подключатся без отдельного развёртывания.
2. Задать `API_TOKEN` в серверном окружении LinguaDesk, `LINGUADESK_API_TOKEN` с тем же значением и `LINGUADESK_API_URL=http://127.0.0.1:3000` в окружении n8n. Секреты не вставлять в JSON.
3. Импортировать workflow. Для входного Webhook выбрать Header Auth credential с именем заголовка `X-LinguaDesk-Key`; значение получать выражением из `LINGUADESK_INBOUND_KEY` окружения n8n. Проверить, что политика вашей установки допускает доступ к этим env-переменным. При запрете оставить workflow выключенным до настройки разрешённого хранилища секретов.
4. Использовать тестовый Webhook URL с заголовком и JSON `{ "text": "Hello, my order is late", "synthetic": true }`.
5. Убедиться, что возврат содержит `status: review`, а в операторском журнале появилось обращение. Подтверждение доступно в UI, не во входном workflow.

Workflow выключен по умолчанию. Сохранение успешных, ошибочных и ручных выполнений отключено в шаблоне; проверьте фактическую конфигурацию n8n перед передачей каких-либо данных.

Источники: [Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook), [HTTP Request](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest), [Respond to Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.respondtowebhook).
